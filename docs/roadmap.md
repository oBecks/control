# Roadmap & status

Last updated 2026-09-26.

## Supported devices

Yeelight lights (bulbs, strips), Tuya / Smart Life Wi-Fi plugs (after a Link), and Broadlink RM infrared hubs: ACs through the Signal Library's Code Sets, TVs, fans and anything else through Learning. Every user starts empty and builds their home by scanning their own network. Device data lives in `%LOCALAPPDATA%\Control`, never in the repo.

## Built

- Engine: Scan (Yeelight, Broadlink, Tuya), Registry (stable uid, IP moves, Offline, New flags, renames), adapters (Yeelight light, Tuya plug, Broadlink transmitter incl. Learning), Signal Library (SmartIR climate/media_player/fan), Code Set Finder, button Remote Devices (Power Toggle vs discrete on/off), FastAPI, CLI.
- Web UI: style guide, Home (Tiles, Device Controls as sheet/side panel, rename), Add devices (Scan, Tuya Link, hub card → AC finder / TV / fan / other with Learning), Settings (theme, Phone access).
- Phone access ([ADR 0003](adr/0003-phone-access-approved-browsers-over-lan-http.md)): the Engine serves the built UI; Settings → Phone access opens a second listener on the LAN address (`api/lan.py`); `api/access.py` gates every non-local request (Approved Browsers with a code, Host/Origin checks). PWA-lite: manifest + icons, no service worker. Tried on real phones: the iPhone Home Screen app opens full screen like a separate app; Android Chrome's home-screen shortcut opens a normal Chrome tab (expected without HTTPS).
- Desktop App ([ADR 0004](adr/0004-desktop-app-per-user-installer-engine-inside.md)): `src/control/desktop/` runs the Engine in a thread, the Window (pywebview) and a tray icon (pystray); single instance via a named mutex, attaches to an Engine already on the port. Closing hides the Window (Windows signing out still closes it); the first close shows a one-time notification. Settings → Phone access warns when Windows Firewall has Block rules for Control (left by a missed or cancelled "Allow access?" prompt, which Windows never shows again, even after a reinstall). Settings → Desktop app: Start with Windows (HKCU Run key, `autostart.py`) and update notices (`updates.py` checks GitHub Releases at start and daily). `packaging/`: PyInstaller spec (one folder), Inno Setup script (per user, pre-ticked Start with Windows, `AppMutex`, uninstall asks about data), `build.py`. `.github/workflows/release.yml` builds and publishes on a `vX.Y.Z` tag. Released as v0.1.0 (https://github.com/oBecks/control/releases/tag/v0.1.0); v0.2.0 adds the Assistant (v0.2.1: its Control.exe was missing httpx; the release workflow now checks `Control.exe --mcp` answers, `packaging/check_mcp.py`); installer, uninstall and the release Action tested.
- Assistant ([ADR 0005](adr/0005-assistant-through-a-local-mcp-server.md)): `Control.exe --mcp` (`src/control/assistant/server.py`, `mcp` SDK) is a stdio MCP server and an Engine Client over HTTP. Tools: `list_devices` (optionally with state), `get_device` (read-only), `set_power`, `set_light`, `set_climate`, `press_button`; Devices by name (any case, or a unique part of it) or uid. If no Engine answers it starts `Control.exe --hidden`, detached. Settings → Assistant: Connect Claude / Disconnect (`assistant/claude.py` merges an `mcpServers.control` entry into Claude Desktop's config, regular and Store install, `.bak` first) and the `claude mcp add` command for Claude Code; the uninstaller runs `Control.exe --disconnect-claude`. Tested over real stdio against the real home, from source and as the packaged Control.exe, through a Node client as Claude launches it: reads, a light's colour, auto-start, and non-English text on the pipes. Control survives the session under Node's Job Object; under the Python SDK's client (kill-on-close, no breakaway) it stops with the session.
- Groups: `groups` + `group_members` tables in the Registry (forgetting a Device takes it out of its Groups; an empty Group goes too), `engine/groups.py` (control surface: light or climate when every member is one, otherwise power; merged features keep only what every member supports; on while any member is on, the first member that's on leads colour/mode), `/api/groups` (CRUD, and `/state` reading or changing every member in parallel, each on its own Registry connection; members that don't answer are listed under `failed`, and only all failing is an error). `DeviceOut.group_problem` says why a Device can't join (a Power Toggle, no On/Off). Home: a Groups section at the top, "New group" in the header, Group Controls (the merged controls plus each member, which opens its own controls) and the Group editor in the side panel or sheet. A Group's reading carries its members' readings, so Home doesn't read grouped Devices twice. Assistant: `get_device`, `set_power`, `set_light`, `set_climate` take a Group too; `create_group`, `edit_group`, `delete_group` (marked `made_by: assistant`, shown in Group Controls).
- Tooling: `npm run check` (eslint, prettier, svelte-check, vitest) + 125 pytest tests; GitHub Action in `.github/workflows/check.yml` (passing on the public repo https://github.com/oBecks/control).

## Next steps (in the order the user chose, 2026-09-26)

Terms are in [CONTEXT.md](../CONTEXT.md) (Group, Hotkey, Dashboard, Automation, Person, Scene).

1. ~~Groups~~: built (see above). Not tried yet on the real lights and plug: switching a Group.
2. **Hotkeys** ([ADR 0007](adr/0007-hotkeys-registered-with-windows-no-keyboard-hook.md)): keys on the PC that toggle or set a Device or Group, or press a remote button. "Run Automation" arrives with Automations and "run Scene" with Scenes. Supported forms: a combination, a single spare key (F13, media keys, Bluetooth buttons that act as keys), a sequence (Ctrl+Alt+L, then 1), a double or long press, and hold-to-dim. They work in any app and any keyboard layout. Control only ever hears its own keys (no keyboard hook), and those keys go only to Control, so the Hotkeys screen suggests spare keys. A small overlay near the tray confirms the action, shows a sequence's choices, and shows the dimming level. They're set up on a Hotkeys screen in Settings (record by pressing the keys; warns when keys are taken) and with "Add Hotkey" in a Device's, Group's or Automation's controls. The Assistant can create them too.
3. **Dashboards**: named screens the user arranges, stored in the Engine and the same on every browser. An Edit mode offers drag and drop on a snapping grid with a few item sizes, on phone and desktop alike. It's one layout that reflows on narrow screens. Items: Device and Group Tiles, big controls (a slider, colour wheel or AC temperature right in place), remote pads (a TV or fan remote's buttons laid out like the remote), Automation run buttons (and Scene buttons once Scenes exist), headings, a clock, and who's home. Each browser can pick a Dashboard to open to instead of Home (e.g. the phone as a "smart control"). The Assistant doesn't edit Dashboards.
4. **Automations** ([ADR 0006](adr/0006-automations-run-in-the-engine.md)): the Engine runs them. You make them in the app's When → Then builder or by describing them to the Assistant (new MCP tools; active right away, marked as made by the Assistant). Each one has an on/off switch and a run history. Missed timed runs are skipped and logged.
   - **Phase 1**: triggers for time and weekdays, sunrise/sunset (needs a location), a Device changing state (Remote Devices: Assumed State only), a Device going Offline/online, and manual run (a button, or asking the Assistant). Steps: control Devices and Groups, wait, conditions (Device state, time window, and/or), and notify (Windows notification plus a notice in the UI).
   - **Phase 2**: presence (People: phones marked as a Person's, arrives/leaves, first home/last out), PC events (wakes, you log in, Control starts), web links (a secret URL per Automation, LAN only), and "undo after / while" (back to how it was after N minutes, or keep on while a condition holds).
5. **Scenes**: a chip row on top of Home, plus a Scene button on Dashboards, a "run Scene" step in Automations, and Assistant tools. Until then, Automations set several Devices directly.
6. **Before promoting Control widely**: code signing (SmartScreen), and the Tuya Link's borrowed identity (ADR 0002).
7. Later: a proper Android install and phone push notifications (both need HTTPS on the LAN: a local certificate authority, see ADR 0003), running the Engine on an always-on box (Raspberry Pi etc.) so phones and Automations work while the PC is off, Rooms, Hubs & Bridges in Settings, a plain-language automation box inside the app (would need an API key), Bluetooth, more brands, public release.

## Open items to raise with the user

- **Before any public release**: the Tuya Link borrows Home Assistant's app identity ([ADR 0002](adr/0002-tuya-link-borrows-home-assistant-identity.md)); ADR 0004 accepts shipping it in GitHub releases for now. Local Keys are sealed with Windows DPAPI (`engine/vault.py`); an always-on box (Linux) would need its own store, since `vault` passes text through there.
- Philips remotes (RC5/RC6) flip a toggle bit per press. If a learned Philips button only works every other time, that's the cause.

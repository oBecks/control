# Roadmap & status

Last updated 2026-09-27 (Automations: run from a Hotkey or a Dashboard).

## Supported devices

Yeelight lights (bulbs, strips), Tuya / Smart Life Wi-Fi plugs (after a Link), and Broadlink RM infrared hubs: ACs through the Signal Library's Code Sets, TVs, fans and anything else through Learning. Every user starts empty and builds their home by scanning their own network. Device data lives in `%LOCALAPPDATA%\Control`, never in the repo.

## Built

- Engine: Scan (Yeelight, Broadlink, Tuya), Registry (stable uid, IP moves, Offline, New flags, renames), adapters (Yeelight light, Tuya plug, Broadlink transmitter incl. Learning), Signal Library (SmartIR climate/media_player/fan), Code Set Finder, button Remote Devices (Power Toggle vs discrete on/off), FastAPI, CLI.
- Web UI: style guide, Home (Tiles, Device Controls as sheet/side panel, rename), Add devices (Scan, Tuya Link, hub card → AC finder / TV / fan / other with Learning), Settings (theme, Phone access).
- Phone access ([ADR 0003](adr/0003-phone-access-approved-browsers-over-lan-http.md)): the Engine serves the built UI; Settings → Phone access opens a second listener on every private address of a real (not virtual) adapter, shows the Wi-Fi/Ethernet one, and rebinds within 30 s when the addresses change, telling Settings the old address moved (`api/lan.py`, tested for real on loopback in `tests/test_lan.py`); `api/access.py` gates every non-local request (Approved Browsers with a code, Host/Origin checks). PWA-lite: manifest + icons, no service worker. Tried on real phones: the iPhone Home Screen app opens full screen like a separate app; Android Chrome's home-screen shortcut opens a normal Chrome tab (expected without HTTPS).
- Desktop App ([ADR 0004](adr/0004-desktop-app-per-user-installer-engine-inside.md)): `src/control/desktop/` runs the Engine in a thread, the Window (pywebview) and a tray icon (pystray); single instance via a named mutex, attaches to an Engine already on the port. Closing hides the Window (Windows signing out still closes it); the first close shows a one-time notification. Settings → Phone access warns when Windows Firewall has Block rules for Control (left by a missed or cancelled "Allow access?" prompt, which Windows never shows again, even after a reinstall). Settings → Desktop app: Start with Windows (HKCU Run key, `autostart.py`) and update notices (`updates.py` checks GitHub Releases at start and daily). `packaging/`: PyInstaller spec (one folder), Inno Setup script (per user, pre-ticked Start with Windows, `AppMutex`, uninstall asks about data), `build.py`. `.github/workflows/release.yml` builds and publishes on a `vX.Y.Z` tag. Released as v0.1.0 (https://github.com/oBecks/control/releases/tag/v0.1.0); v0.2.0 adds the Assistant (v0.2.1: its Control.exe was missing httpx; the release workflow now checks `Control.exe --mcp` answers, `packaging/check_mcp.py`); v0.3.0 adds Streamers (Android TV); v0.7.2 leaves Pillow's unused codecs out (`Control.spec` `pillow_unused`, 10 MB less); installer, uninstall and the release Action tested.
- Assistant ([ADR 0005](adr/0005-assistant-through-a-local-mcp-server.md)): `Control.exe --mcp` (`src/control/assistant/server.py`, `mcp` SDK) is a stdio MCP server and an Engine Client over HTTP. Tools: `list_devices` (optionally with state), `get_device` (read-only), `set_power`, `set_light`, `set_climate`, `press_button`; Devices by name (any case, or a unique part of it) or uid. If no Engine answers it starts `Control.exe --hidden`, detached. Settings → Assistant: Connect Claude / Disconnect (`assistant/claude.py` merges an `mcpServers.control` entry into Claude Desktop's config, regular and Store install, `.bak` first) and the `claude mcp add` command for Claude Code when the `claude` CLI is on PATH; the status also tells apart a partial connection (one of the two installs) and a config file Control won't touch; the uninstaller runs `Control.exe --disconnect-claude`. Tested over real stdio against the real home, from source and as the packaged Control.exe, through a Node client as Claude launches it: reads, a light's colour, auto-start, and non-English text on the pipes. Control survives the session under Node's Job Object; under the Python SDK's client (kill-on-close, no breakaway) it stops with the session.
- Groups: `groups` + `group_members` tables in the Registry (forgetting a Device takes it out of its Groups; an empty Group goes too), `engine/groups.py` (control surface: light or climate when every member is one, otherwise power; merged features keep only what every member supports; on while any member is on, the first member that's on leads colour/mode), `/api/groups` (CRUD, and `/state` reading or changing every member in parallel, each on its own Registry connection; members that don't answer are listed under `failed`, and only all failing is an error). `DeviceOut.group_problem` says why a Device can't join (a Power Toggle, no On/Off). Home: a Groups section at the top, "New group" in the header, Group Controls (the merged controls plus each member, which opens its own controls) and the Group editor in the side panel or sheet. A Group's reading carries its members' readings, so Home doesn't read grouped Devices twice. Assistant: `get_device`, `set_power`, `set_light`, `set_climate` take a Group too; `create_group`, `edit_group`, `delete_group` (marked `made_by: assistant`, shown in Group Controls).
- Streamers, Android TV (roadmap step 2, first part): `scanners/media_scanner.py` browses mDNS once per Scan (`_androidtvremote2`, `_googlecast` for the model, and Apple TV / Fire TV / Cast-only devices as Unsupported; an Android TV record the browse missed is asked for by its Cast name). `adapters/androidtv_streamer.py` keeps one `androidtvremote2` connection per Streamer on a background event loop; one client certificate for every device, its key encrypted with a `vault`-sealed password (`%LOCALAPPDATA%\Control\androidtv\`). `engine/streamer.py`: button names shared with infrared TVs, the app catalogue, open-app names. Registry `streamers` table (TV or box, App Shortcuts). API: `/api/links/androidtv/{uid}` (start, `/code`, cancel), `/api/streamers/{uid}` (setup), `/catalogue`; `open_app` on the state endpoint. UI: `add/StreamerSetup.svelte` (Link → box or TV → name → apps), `controls/StreamerControls.svelte`, `streamer/AppPicker.svelte`. Assistant: `open_app`, `press_button` and `set_power` for Streamers. Tried on the real Shield and a yes+ box (2026-09-26): Link, open app, Home, off, on. **Apps open by link, not by package**: both boxes refuse `market://launch?id=…` and `intent:` links, so catalogue entries carry a link where one is known (YouTube, Netflix, Spotify `https://open.spotify.com`, Apple TV and Stremio `stremio://` confirmed); yes+ (`il.co.yes.yesplus`) declares no link at all, so [ADR 0008](adr/0008-streamers-open-apps-by-link-adb-optional.md) adds two ways for such apps: adb (`adapters/android_adb.py`, `adb-shell`), an optional second step of the Link that also lists the apps really installed (`PUT /api/streamers/{uid}/adb`, `streamer/AdbSetup.svelte`, offered at setup and when a linkless app is added), and otherwise the app's Play Store page with OK pressed on Open. A sleeping box is woken before an app opens. Both tried on the Shield: yes+ opens. The Shield going to sleep didn't switch its TV off (HDMI-CEC setting on the Shield).

Second part (0.5.0): double and long presses and sequences (`engine/hotkeys.py` `Trigger`, keys written "F13 (double)", "F13 (long)", "Ctrl+Alt+L, then 1"; `Presses` and the sequence window in `desktop/hotkeys.py`; "Pressed" in the editor). Notices show at the top of every page until dismissed, and the Desktop App long-polls `/api/notices/watch` to show them as Windows notifications from the tray. The "what it does to a Device or Group" fields moved from the Hotkey editor into `lib/hotkeys/ActionFields.svelte`, shared by both. Assistant tools `list_automations`, `get_automation`, `create_automation`, `edit_automation`, `set_automation_enabled`, `run_automation`, `delete_automation`. Tried against a copy of the real database on a second Engine (sunset for Jerusalem, a notify-only Run, notices), without running Actions on the real devices.

     - Shape: When (Triggers, any starts a Run) → Only if (Conditions, all or any, no nesting) → Then (Actions in order). No If / else Action yet.
     - Triggers: a time on weekdays; sunrise/sunset ± offset on weekdays; a Device or Group turns on/off, optionally "stays so for N min" (a Group is on while any member is); a Streamer opens an app; a Device goes Offline / comes online. No "every N minutes".

Built as "it's dark" (sunset to sunrise) or "it's light", since "after sunset" at 01:00 means dark to people, not "until midnight".

     - Runs: restart on a new Trigger; abandoned and notified if the PC sleeps or Control quits mid-Run; carry on and notify after a failed Action; chaining with a loop guard; running by hand skips Conditions; an Automation without Triggers is manual-only; last 50 Runs kept.

     - Forgetting a Device / deleting a Group drops only the parts naming it; losing its last Trigger or Action switches the Automation off as "needs attention".

8. **Light on the PC** (asked for 2026-09-26): Control should use as little CPU, GPU and RAM as possible while staying instant when it's needed (a Hotkey, opening the Window, a phone). Measured on 0.4.0, in the tray with the Window closed, 20 s on a 6-core PC: Control (Engine, tray, Hotkey listener) 0.3% CPU and 188 MB; the Window's WebView2 processes 0.15% CPU and ~425 MB even though the Window is hidden; Claude's two `--mcp` helpers ~0% CPU and 80 MB each (only while Claude runs); GPU nothing while hidden. Ideas, measure each before and after the same way:
   - Done (2026-09-26, v0.6.0), measured the same way:
     - **The Window is released 5 minutes after it's closed** (`KEEP_WINDOW` in `desktop/app.py`): its 6 WebView2 processes (~220 MB private, ~385 MB working set) end, and opening Control makes it again in about half a second on the page background. A plain hidden WinForms form (the "keeper") keeps pywebview's GUI loop alive meanwhile, and ends it when Windows signs out. The Engine, tray and Hotkey listener don't depend on the Window, so phones and Hotkeys work the same.
     - **A closed Window's page now knows it's hidden.** WebView2's WinForms control never passed the form hiding on, so the UI kept polling (and so reading devices) all day in the tray. While kept, WebView2 CPU went from 0.29% to 0.04%.
     - **The tray's status line is read when its menu opens**, not every 5 s.
     - **The Hotkey watch sleeps until something changes** (it woke twice a second to notice recording running out).
     - **The Engine no longer imports `mcp`** (~22 MB and ~0.85 s at startup) just for a header name.
   - Left, smaller: brand libraries imported only when needed (tinytuya ~5 MB, the adapters ~7 MB); the `--mcp` helpers are ~51 MB of `mcp` + `httpx` themselves; the Window's .NET runtime costs ~36 MB while Control runs; pywebview's own 500 ms timer on the GUI thread.

     - **Local certificate authority** (ADR 0003): the Engine makes its own authority once (key sealed with DPAPI like Local Keys), issues a certificate for the PC's LAN addresses and reissues it when `api/lan.py` sees them change; keep plain HTTP for a while so Approved Browsers keep working. Every phone installs the authority once, which Settings → Phone access walks through: iPhone installs a profile, then turns on full trust in Settings → General → About → Certificate Trust Settings; Android 11+ can't install it from the browser, only from Settings → Security (Chrome trusts it then). Free and works without the internet.
     - **A real domain with Let's Encrypt**, with Vercel as the helper: buy a domain on Vercel and let it manage the DNS; a Vercel function gives each install its own name (`abc123.<domain>`) pointing at the PC's LAN address, and places the DNS-01 proof through Vercel's API when the Engine asks Let's Encrypt for a certificate. Phones trust it with no setup. The Control UI itself can't be hosted on Vercel: an HTTPS page there can't call the Engine's plain HTTP (mixed content), so the PC still needs its own certificate. Catches: ~$10–15 a year for the domain and a service on the internet to keep up; Let's Encrypt allows ~50 certificates a week per domain (fine for a few homes, a public release needs the limit raised or the domain on the Public Suffix List); the function must be locked down so nobody can point names elsewhere; some routers block public names that point at home addresses (DNS rebinding protection), and there it doesn't work at all.

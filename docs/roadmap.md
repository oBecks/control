# Roadmap & status

Last updated 2026-09-26.

## Supported devices

Yeelight lights (bulbs, strips), Tuya / Smart Life Wi-Fi plugs (after a Link), and Broadlink RM infrared hubs: ACs through the Signal Library's Code Sets, TVs, fans and anything else through Learning. Every user starts empty and builds their home by scanning their own network. Device data lives in `%LOCALAPPDATA%\Control`, never in the repo.

## Built

- Engine: Scan (Yeelight, Broadlink, Tuya), Registry (stable uid, IP moves, Offline, New flags, renames), adapters (Yeelight light, Tuya plug, Broadlink transmitter incl. Learning), Signal Library (SmartIR climate/media_player/fan), Code Set Finder, button Remote Devices (Power Toggle vs discrete on/off), FastAPI, CLI.
- Web UI: style guide, Home (Tiles, Device Controls as sheet/side panel, rename), Add devices (Scan, Tuya Link, hub card → AC finder / TV / fan / other with Learning), Settings (theme, Phone access).
- Phone access ([ADR 0003](adr/0003-phone-access-approved-browsers-over-lan-http.md)): the Engine serves the built UI; Settings → Phone access opens a second listener on the LAN address (`api/lan.py`); `api/access.py` gates every non-local request (Approved Browsers with a code, Host/Origin checks). PWA-lite: manifest + icons, no service worker. Tried on real phones: the iPhone Home Screen app opens full screen like a separate app; Android Chrome's home-screen shortcut opens a normal Chrome tab (expected without HTTPS).
- Desktop App ([ADR 0004](adr/0004-desktop-app-per-user-installer-engine-inside.md)): `src/control/desktop/` runs the Engine in a thread, the Window (pywebview) and a tray icon (pystray); single instance via a named mutex, attaches to an Engine already on the port. Closing hides the Window (Windows signing out still closes it); the first close shows a one-time notification. Settings → Phone access warns when Windows Firewall has Block rules for Control (left by a missed or cancelled "Allow access?" prompt, which Windows never shows again, even after a reinstall). Settings → Desktop app: Start with Windows (HKCU Run key, `autostart.py`) and update notices (`updates.py` checks GitHub Releases at start and daily). `packaging/`: PyInstaller spec (one folder), Inno Setup script (per user, pre-ticked Start with Windows, `AppMutex`, uninstall asks about data), `build.py`. `.github/workflows/release.yml` builds and publishes on a `vX.Y.Z` tag. Released as v0.1.0 (https://github.com/oBecks/control/releases/tag/v0.1.0); v0.2.0 adds the Assistant (v0.2.1: its Control.exe was missing httpx; the release workflow now checks `Control.exe --mcp` answers, `packaging/check_mcp.py`); v0.3.0 adds Streamers (Android TV); installer, uninstall and the release Action tested.
- Assistant ([ADR 0005](adr/0005-assistant-through-a-local-mcp-server.md)): `Control.exe --mcp` (`src/control/assistant/server.py`, `mcp` SDK) is a stdio MCP server and an Engine Client over HTTP. Tools: `list_devices` (optionally with state), `get_device` (read-only), `set_power`, `set_light`, `set_climate`, `press_button`; Devices by name (any case, or a unique part of it) or uid. If no Engine answers it starts `Control.exe --hidden`, detached. Settings → Assistant: Connect Claude / Disconnect (`assistant/claude.py` merges an `mcpServers.control` entry into Claude Desktop's config, regular and Store install, `.bak` first) and the `claude mcp add` command for Claude Code; the uninstaller runs `Control.exe --disconnect-claude`. Tested over real stdio against the real home, from source and as the packaged Control.exe, through a Node client as Claude launches it: reads, a light's colour, auto-start, and non-English text on the pipes. Control survives the session under Node's Job Object; under the Python SDK's client (kill-on-close, no breakaway) it stops with the session.
- Groups: `groups` + `group_members` tables in the Registry (forgetting a Device takes it out of its Groups; an empty Group goes too), `engine/groups.py` (control surface: light or climate when every member is one, otherwise power; merged features keep only what every member supports; on while any member is on, the first member that's on leads colour/mode), `/api/groups` (CRUD, and `/state` reading or changing every member in parallel, each on its own Registry connection; members that don't answer are listed under `failed`, and only all failing is an error). `DeviceOut.group_problem` says why a Device can't join (a Power Toggle, no On/Off). Home: a Groups section at the top, "New group" in the header, Group Controls (the merged controls plus each member, which opens its own controls) and the Group editor in the side panel or sheet. A Group's reading carries its members' readings, so Home doesn't read grouped Devices twice. Assistant: `get_device`, `set_power`, `set_light`, `set_climate` take a Group too; `create_group`, `edit_group`, `delete_group` (marked `made_by: assistant`, shown in Group Controls).
- Streamers, Android TV (roadmap step 2, first part): `scanners/media_scanner.py` browses mDNS once per Scan (`_androidtvremote2`, `_googlecast` for the model, and Apple TV / Fire TV / Cast-only devices as Unsupported; an Android TV record the browse missed is asked for by its Cast name). `adapters/androidtv_streamer.py` keeps one `androidtvremote2` connection per Streamer on a background event loop; one client certificate for every device, its key encrypted with a `vault`-sealed password (`%LOCALAPPDATA%\Control\androidtv\`). `engine/streamer.py`: button names shared with infrared TVs, the app catalogue, open-app names. Registry `streamers` table (TV or box, App Shortcuts). API: `/api/links/androidtv/{uid}` (start, `/code`, cancel), `/api/streamers/{uid}` (setup), `/catalogue`; `open_app` on the state endpoint. UI: `add/StreamerSetup.svelte` (Link → box or TV → name → apps), `controls/StreamerControls.svelte`, `streamer/AppPicker.svelte`. Assistant: `open_app`, `press_button` and `set_power` for Streamers. Tried on the real Shield and a yes+ box (2026-09-26): Link, open app, Home, off, on. **Apps open by link, not by package**: both boxes refuse `market://launch?id=…` and `intent:` links, so catalogue entries carry a link where one is known (YouTube, Netflix, Spotify `https://open.spotify.com`, Apple TV and Stremio `stremio://` confirmed); yes+ (`il.co.yes.yesplus`) declares no link at all, so [ADR 0008](adr/0008-streamers-open-apps-by-link-adb-optional.md) adds two ways for such apps: adb (`adapters/android_adb.py`, `adb-shell`), an optional second step of the Link that also lists the apps really installed (`PUT /api/streamers/{uid}/adb`, `streamer/AdbSetup.svelte`, offered at setup and when a linkless app is added), and otherwise the app's Play Store page with OK pressed on Open. A sleeping box is woken before an app opens. Both tried on the Shield: yes+ opens. The Shield going to sleep didn't switch its TV off (HDMI-CEC setting on the Shield).
- Tooling: `npm run check` (eslint, prettier, svelte-check, vitest) + 150 pytest tests; GitHub Action in `.github/workflows/check.yml` (passing on the public repo https://github.com/oBecks/control).

## Next steps (in the order the user chose, 2026-09-26; TVs added after Groups the same day)

Terms are in [CONTEXT.md](../CONTEXT.md) (Group, Hotkey, Dashboard, Automation, Person, Scene).

1. ~~Groups~~: built (see above). Tried on the real lights 2026-09-26: a "Lights" Group of all three turned them all on and off.
2. ~~TVs and streamers over the network~~: **Android TV built** (see Built, released in v0.3.0). On 2026-09-26 the user moved on to Hotkeys; the rest is in **Future TV work** at the end of this list. Scan finds them, and they become Devices with a real state instead of an Assumed State.
   - **Android TV first** (Google TV, NVIDIA Shield, operator boxes such as yes+): one adapter on the Android TV Remote protocol (`androidtvremote2`, mDNS `_androidtvremote2._tcp`). It gives power with real on/off state, volume and mute, the arrow keys, OK, Back and Home, and opening apps. Pairing happens once, with a PIN shown on the TV, like the Tuya Link. Google Cast (`pychromecast`, `_googlecast._tcp`, no pairing) adds what's playing and play/pause/seek.
   - **Android TV: built** (see Built). The user Links the other two yes boxes themselves when they want.
   - **"What's playing" over adb: checked 2026-09-26, not worth building.** `dumpsys media_session` on the Shield: yes+ publishes no media session at all (only an audio player in `dumpsys audio`, so "making sound" at best); Netflix publishes state and position but `metadata: null`, so no title. Revisit with Google Cast. App names and icons over adb need each APK pulled (yes+ 61 MB, Stremio 71 MB) and parsed: left for Dashboards.
   - **Decided 2026-09-26 for the first step (Android TV Remote only, Cast later):** a Shield or yes+ box is a **Streamer** (CONTEXT.md), its own Media Device, separate from the TV (combining a Streamer with its TV's infrared Remote Device comes later). Setup on Add Devices: a Link (type the PIN the TV shows; the certificate is stored like a Local Key), then a name prefilled as "Streamer – …" (a leading "TV" becomes "Streamer"), then tick **Streamer App Shortcuts** from a catalogue with a custom option (pre-ticked: YouTube, Netflix, Spotify, Apple TV, plus yes+ on yes boxes). Android TV can't list installed apps, so the catalogue is Control's own. Device Controls, top to bottom: power, volume −/+ and mute; D-pad with OK, Back, Home; the App Shortcuts with Edit (reorder, remove, add), per Device. The Tile shows the open app's name while on. Streamers can join Groups; the Assistant gets `set_power`, `press_button` (same button names as an infrared TV) and a new `open_app`. All four boxes still answer on 6466/6467/8009 while in standby, so standby is Off, not Offline. Works with any Android TV / Google TV device, not just the user's. A TV that runs Android TV itself (Sony, TCL…) is a TV, not a Streamer: setup asks "a TV, or a box plugged into a TV?", pre-selected from the reported manufacturer/model; only the icon and prefilled name differ. Apple TV, Roku, Fire TV and Cast-only Chromecasts show as Unsupported where a Scan can see them.
   - **Samsung Tizen (future)** (`samsungtvws`, `http://<ip>:8001/api/v2/` reports `PowerState`). The TV asks "Allow?" once.
   - Turning the TV on and off goes through the streamer: waking it sends HDMI-CEC to the TV (Anynet+, EasyLink, SimpLink…), which switches the TV on and to that input. The Device's state is the streamer's, not the TV's, so someone using the TV's own remote can leave them out of step. Fallbacks for a TV that ignores CEC or a streamer that drops off the network in standby: Wake-on-LAN, or an infrared power button through a Hub (let one Device combine the two).
   - Remote pads on Dashboards and the Assistant's `press_button` should work for these too.
   - The user's home has four Android TV devices and a Samsung to test with (see `docs/my-home.local.md`). SSDP got no replies on this PC (probably Windows Firewall); mDNS found everything.
3. **Hotkeys** ([ADR 0007](adr/0007-hotkeys-registered-with-windows-no-keyboard-hook.md)): keys on the PC that toggle or set a Device or Group, or press a remote button. "Run Automation" arrives with Automations and "run Scene" with Scenes. Supported forms: a combination, a single spare key (F13, media keys, Bluetooth buttons that act as keys), a sequence (Ctrl+Alt+L, then 1), a double or long press, and hold-to-dim. They work in any app and any keyboard layout. Control only ever hears its own keys (no keyboard hook), and those keys go only to Control, so the Hotkeys screen suggests spare keys. A small overlay near the tray confirms the action, shows a sequence's choices, and shows the dimming level. They're set up on a Hotkeys screen in Settings (record by pressing the keys; warns when keys are taken) and with "Add Hotkey" in a Device's, Group's or Automation's controls. The Assistant can create them too.
   - **Decided 2026-09-26 for the first build:** a Hotkey = keys + one Device or Group + one action: toggle, set (any StateIn field), step up/down (brightness 10%, AC temperature 1°, editable per Hotkey), press a button (infrared remote or Streamer), open a Streamer app. Holding repeats steps and presses; the rest fire once. Keys: combinations, single spare keys and hold-to-repeat now; sequences and double/long presses in a second PR. Set up only on the PC running Control (Settings → Hotkeys, "Add Hotkey" in Device and Group Controls): record by pressing, or pick the key from a list when the Window can't see it; keys taken by another app are marked. Overlay near the tray (~1.5 s, no focus). The Assistant lists, creates and deletes them (made_by, like Groups). Forgetting the target deletes its Hotkeys.
4. **Dashboards**: named screens the user arranges, stored in the Engine and the same on every browser. An Edit mode offers drag and drop on a snapping grid with a few item sizes, on phone and desktop alike. It's one layout that reflows on narrow screens. Items: Device and Group Tiles, big controls (a slider, colour wheel or AC temperature right in place), remote pads (a TV or fan remote's buttons laid out like the remote), Automation run buttons (and Scene buttons once Scenes exist), headings, a clock, and who's home. Each browser can pick a Dashboard to open to instead of Home (e.g. the phone as a "smart control"). The Assistant doesn't edit Dashboards.
5. **Automations** ([ADR 0006](adr/0006-automations-run-in-the-engine.md)): the Engine runs them. You make them in the app's When → Then builder or by describing them to the Assistant (new MCP tools; active right away, marked as made by the Assistant). Each one has an on/off switch and a run history. Missed timed runs are skipped and logged.
   - **Phase 1**: triggers for time and weekdays, sunrise/sunset (needs a location), a Device changing state (Remote Devices: Assumed State only), a Device going Offline/online, and manual run (a button, or asking the Assistant). Steps: control Devices and Groups, wait, conditions (Device state, time window, and/or), and notify (Windows notification plus a notice in the UI).
   - **Phase 2**: presence (People: phones marked as a Person's, arrives/leaves, first home/last out), PC events (wakes, you log in, Control starts), web links (a secret URL per Automation, LAN only), and "undo after / while" (back to how it was after N minutes, or keep on while a condition holds).
6. **Scenes**: a chip row on top of Home, plus a Scene button on Dashboards, a "run Scene" step in Automations, and Assistant tools. Until then, Automations set several Devices directly.
7. **Small fixes** (found 2026-09-26; each small, can go before or after Hotkeys):
   - **Opening an app answers too early.** Over adb, `open_app` returns before the Streamer reports the new app, so the reply (and the Assistant) still says "Home screen" for a moment. After opening, wait until the Streamer reports the app (a few seconds at most) before reading its state.
   - **The installer can't close Claude's `Control.exe --mcp`**: it has no window, so Inno Setup's "close applications" fails and the user must stop it by hand. Have the installer stop `Control.exe --mcp` itself before copying files (e.g. `taskkill` in `PrepareToInstall`), since Claude restarts it anyway.
   - **Say "restart Claude" after an update, not only before.** The update notice only shows while an update waits, so running the installer directly says nothing. After a version change, the Assistant section in Settings (and the Window once) should say "Control was updated to X. Restart Claude to get the new Assistant tools", until an MCP server of the new version talks to the Engine (it could send its version in a header) or the user dismisses it.
8. **Before promoting Control widely**: code signing (SmartScreen), and the Tuya Link's borrowed identity (ADR 0002).
9. Later: a proper Android install and phone push notifications (both need HTTPS on the LAN: a local certificate authority, see ADR 0003), running the Engine on an always-on box (Raspberry Pi etc.) so phones and Automations work while the PC is off, Rooms, Hubs & Bridges in Settings, a plain-language automation box inside the app (would need an API key), Bluetooth, more brands, public release.

## Open items to raise with the user

- **Before any public release**: the Tuya Link borrows Home Assistant's app identity ([ADR 0002](adr/0002-tuya-link-borrows-home-assistant-identity.md)); ADR 0004 accepts shipping it in GitHub releases for now. Local Keys are sealed with Windows DPAPI (`engine/vault.py`); an always-on box (Linux) would need its own store, since `vault` passes text through there.
- Philips remotes (RC5/RC6) flip a toggle bit per press. If a learned Philips button only works every other time, that's the cause.
10. **Future TV work** (moved out of step 2 on 2026-09-26, details under step 2): Samsung Tizen TVs (the user's 75" at .111); Google Cast (what's playing, play/pause, though yes+ and Netflix give no titles over adb); one Device combining a Streamer with its TV's infrared Remote Device (e.g. Shield + Philips), which needs its own design round; the Shield's TV staying on when it sleeps (HDMI-CEC); real app names and icons over adb (APK pulls, maybe with Dashboards); a yes+ link if yes ever publishes one.
